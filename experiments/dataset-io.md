# P12 dataset-io — 입력 데이터셋 읽기와 `run` 뼈대

## 결론
채택 제안. SPEC §1 입력(`images/cam{F,R,L}/cam{F,R,L}_{번호:04}.jpg`, `gps.txt`)을 읽어
STRIDE 로 프레임을 고르고, 세 카메라가 모두 있는 프레임만 위치 0, 1, … 로 매긴다.
GPS 는 첫 기록을 원점으로 동-북-위(m)로 바꾼다(`geo.rs` 그대로 사용).
SPEC §3.5 구역 분할 `[start−OVL, start+SPAN+OVL) ∩ [0, n)` 을 같은 모듈에 두었고,
80위치·SPAN 12·OVL 2 의 경계가 손 계산과 일치한다.
`skylens-stream run` 은 지금은 위치 수·사진 수·구역 목록을 출력하고 `preview/ refined/ snapshots/` 만 만든다.

## F-041·F-042·F-043·F-064·F-065·F-044 (데이터셋 읽기 보완)
결론: 채택 제안. GPS 는 사진(카메라, 프레임)별로 찾는다. 드론 3대가 같은 프레임에 서로 다른 GPS 를
가지는 것이 정상이므로 같은 (카메라, 프레임)에 다른 값이 두 번 나올 때만 중복 오류다. `Position` 은
카메라별 `image_geo`·`image_enu` 와 그 평균(편대 중심) `geo`·`enu` 를 함께 갖는다. 카메라 접두 없는
줄(`0003`)은 세 카메라 공통이며 카메라별 줄이 우선한다. 카메라별 GPS 가 없고 공통 줄도 없으면
다른 카메라 값으로 메우지 않고 `GpsMissing{camera, frame}` 로 멈춘다.
사진 번호는 `{:04}` 표기 그대로만 받고, 카메라가 빠진 프레임은 `Dataset::skipped` 에 남겨 `run` 이 보인다.
마지막 구역 처리는 아래 "F-065 다시" 절로 바뀌었다(앞 구역을 늘리지 않고, 앞 구역 안에 통째로 들어가는 꼬리만 버림).

방법·결정 근거:
- 건너뜀 허용 기본 2: 연속 두 곳을 건너뛰면 앞뒤 위치의 실제 간격은 3칸(약 3 m)이다. SPEC §3.2 시간 이웃이
  위치 차 1..5 를 모두 짝지으므로 이 정도는 그대로 짝이 생긴다. 세 곳 이상 빠지면 위치 번호와 실제 거리의
  어긋남이 커지고(위치 1칸 ≈ 1 m 가정), 한 카메라가 뒷부분을 통째로 잃은 경우가 대부분 여기에 걸린다.
  허용은 `DatasetConfig::max_skip_run`·`run --max-skip-run N` 으로 바꾼다. 비율 기준은 두지 않았다 —
  짧은 자료(프레임 0..9)에서 한 장만 빠져도 25% 가 되어 기준을 정하기 어렵다.
- 위치 번호는 건너뛴 프레임을 빼고 다시 0,1,… 로 매긴다(위치 번호 유지 대신 보고·오류를 택함).
  번호를 비워 두면 구역 분할·스냅샷 단계가 모두 빈 위치를 다뤄야 해서다.
- 프레임 고르기는 실제로 있는 프레임 집합에서 (f − f0) 가 STRIDE 배수인 것만 걸러 낸다. 사진이 하나도 없는
  프레임 번호는 건너뜀으로 세지 않는다.
- 구역 분할 꼬리 합치기는 로더 `chunk_ranges` 에만 했다. 스트림 쪽 `split_regions` 는 이 묶음 파일이 아니라
  그대로이며, 둘을 하나로 묶는 일은 남았다.

## F-065 다시 — 구역 분할을 스트림 쪽과 같은 규칙으로
결론: 채택 제안. 로더 `chunk_ranges` 를 "start ≥ 1 인 구역은 start + OVL < n 일 때만 만든다" 로 바꿨다.
이 조건이 거짓이면 그 구역 [start−OVL, n) 은 앞 구역 [start−SPAN−OVL, n) 안에 통째로 들어가 새 위치가 0 이므로
버리는 것이 맞고, 참이면 앞 구역 끝 start+OVL 너머 위치가 1개 이상이다. 남는 구역은 모두 SPEC §3.5 범위
그대로다(앞 구역을 늘리지 않음). 지난번 로더 규칙(새 위치 ≤ OVL 이면 앞 구역 끝을 늘려 합침)은
n=15·16(12/2)에서 [0..15]·[0..16] 을 만들어 스트림 쪽 `split_regions`(feat/stream-hardening 3d831e6)의
[0..14, 10..15]·[0..14, 10..16] 과 달랐다. 이제 두 함수는 같은 n·SPAN·OVL 에 같은 범위를 낸다.

| 경우 (n, SPAN, OVL) | 정답 표 | 결과 |
|---|---|---|
| 80, 12, 2 | 0..14, 10..26, 22..38, 34..50, 46..62, 58..74, 70..80 (7) | 일치 |
| 81 / 82 / 86, 12, 2 | 앞 6구역 + 70..81 / 70..82 / 70..86 (7, start 84 는 84+2 ≥ n 이라 버림) | 일치 |
| 87, 12, 2 | 앞 6구역 + 70..86, 82..87 (8) | 일치 |
| 13 / 14 / 15, 12, 2 | 0..13 / 0..14 / 0..14, 10..15 | 일치 |
| 17 / 26 / 27, 12, 2 | 0..14,10..17 / 0..14,10..26 / 0..14,10..26,22..27 | 일치 |
| 10 / 11, 4, 2 | 0..6,2..10 / 0..6,2..10,6..11 | 일치 |
| 9 / 10, 4, 0 | 0..4,4..8,8..9 / 0..4,4..8,8..10 | 일치 |
| 0, 12, 2 · 10, 0, 2 | 빈 목록 | 일치 |
| n∈[1,200] × SPAN∈{1,4,12} × OVL∈{0,2,5} | 합집합 0..n, 이웃 구역 빈틈 없음, 구역 i≥1 끝 > 앞 구역 끝, i 번째 구역 = SPEC 범위(start=i·SPAN), 버린 start 는 마지막 구역 안에 통째로 포함 | 1800 경우 통과 |
| 합성 기본 장면 STRIDE 3 → 27 곳 | 0..14, 10..26, 22..27 (24+2 < 27 이라 꼬리 남김) | 일치 |

- OVL ≥ SPAN(예: SPAN 1, OVL 2)이면 앞쪽 여러 구역이 0 에서 시작한다. SPEC 범위 그대로의 결과라 시험은
  start 가 줄지 않음(≥)만 본다. 포함 관계는 "끝이 늘어남"으로 막힌다.
- 같은 함수가 두 벌이다: `dataset::chunk_ranges`(Range 목록)와 `stream::split_regions`(Region{index,start,lo,hi}).
  `stream.rs` 는 이 묶음 파일이 아니라 고치지 않았다. 스트림 쪽 수정(feat/stream-hardening)이 main 에 들어오면
  `split_regions` 가 `chunk_ranges` 를 불러 Region 을 만들도록 하나로 줄이는 일이 남는다. 지금 main 의
  `split_regions` 는 아직 꼬리를 버리지 않는다(26/12/2 → 세 구역, 마지막 22..26 새 위치 0).

## F-065 경계 표·두 함수 일치 (main 합친 뒤 다시 확인)
결론: 로더 쪽 처리 유지. main(6f14401)에 스트림 쪽 꼬리 합침이 들어와 `stream::split_regions` 와
`dataset::chunk_ranges` 가 같은 규칙이 되었고, 이를 시험으로 묶었다(`chunks_match_stream_regions`:
n∈[1,200] × SPAN∈{4,12} × OVL∈{0,2}, 800 경우에서 `lo..hi` 목록이 같음). 한쪽 규칙만 바뀌면 이 시험이 깨진다.
80 곳 전후 경계 위치 수 정답 표(`chunks_boundary_table_12_2`, SPEC §3.5 범위식 손 계산):

| n (SPAN 12, OVL 2) | 정답 구역 | 구역 수 | 근거 |
|---|---|---|---|
| 72 | 0..14, 10..26, 22..38, 34..50, 46..62, 58..72 | 6 | start 72 = n 이라 없음 |
| 73 | … 46..62, 58..73 | 6 | start 72: 72+2 ≥ 73 → 꼬리 70..73 은 58..73 안 |
| 74 | … 46..62, 58..74 | 6 | 72+2 ≥ 74 → 꼬리 70..74 는 58..74 안 |
| 75 | … 58..74, 70..75 | 7 | 72+2 < 75, 새 위치 74 하나 |
| 80 | … 58..74, 70..80 | 7 | 기존 정답 그대로 |
| 84 | … 58..74, 70..84 | 7 | start 84 = n 이라 없음 |
| 85 | … 58..74, 70..85 | 7 | start 84: 84+2 ≥ 85 → 꼬리 82..85 는 70..85 안 |

모든 표에서 각 구역 끝이 앞 구역 끝보다 뒤(새 위치 0 인 구역 없음). 함수는 여전히 두 벌이며
(`stream.rs` 는 이 묶음 파일이 아님), 하나로 줄이는 대신 일치 시험으로 고정했다.

## F-038 사진 폴더 구조 (합성 출력을 로더가 그대로 읽기)
결론: 로더가 두 구조를 모두 읽는다 — 평평한 `images/cam{F,R,L}_{번호:04}.jpg`(합성 출력·README 형식)와
카메라별 하위 폴더 `images/cam{F,R,L}/cam{F,R,L}_{번호:04}.jpg`. 카메라마다 두 곳을 함께 훑으므로
섞어 놓아도 된다. 같은 카메라·같은 프레임 사진이 양쪽에 있으면(또는 `camF_3.jpg`·`camF_0003.jpg`
처럼 같은 번호가 둘이면) `DuplicateImage{first, second}` 오류로 멈춘다 — 어느 쪽을 써야 할지 모르기 때문.
SPEC §1 은 파일명만 정하므로 두 구조 모두 SPEC 에 맞는다. 합성 생성기와 README 는 그대로 둔다.
`Position::images` 는 이제 실제로 찾은 경로를 담는다(`image_path` 는 하위 폴더 형식 경로를 만드는 도우미로 남김).
카메라 하나가 하위 폴더도 없고 평평한 사진도 없으면 전과 같이 `Missing(images/camX)`.

| 검증(통합 시험 `crates/core/tests/dataset_synth.rs`) | 정답(합성 설정) | 결과 |
|---|---|---|
| 기본 장면 80 위치(렌더 96×54) `write_dataset` → gps.txt 행 수 | 80 × 3 = 240 | 240 |

합성 세계 원점의 접평면 차이는 수 m / 지구 반지름 × 이동 200 m ≈ 0.1 mm. 위치 간격 2.5 m 보다 훨씬 작아
위치가 하나라도 밀리면 실패한다.
