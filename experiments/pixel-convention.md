# pixel-convention — 특징점 좌표를 카메라 화소 중심 규약으로

## 결론
채택 제안. `detect_and_describe`(따라서 `detect`)가 내보내는 `Keypoint::x, y` 를 카메라 모형과 같은
화소 중심 규약(화소 (i, j) 의 중심 = (i + 0.5, j + 0.5))으로 바꿨다. 호출자는 더 이상 +0.5 를 기억할 필요가 없고
`Keypoint::pixel()` 을 `Intrinsics::to_normalized`·`Camera::unproject` 에 그대로 넣는다.
변경 전 출력과의 관계는 비트 단위로 확인했다: 개수·순서·σ·응답·방향·기술자는 같고 x, y 만 정확히 f32 +0.5 이동했다.
고정 합성 영상(480×270)의 검출 결과 해시 회귀 시험을 넣었고, 흐림 누산 순서를 일부러 뒤집으면 이 시험이 실패함을 확인했다.
`experiment/features` 위에서 땄다.

## 방법
- 옥타브 o 의 화소 j 는 원본 화소 2^o·j 를 뽑은 것(`downsample`, 짝수 화소 추출)이라 중심이 원본 연속 좌표 2^o·j + 0.5 에 있다.
  그래서 옥타브 안 화소 번호 좌표 u 를 2^o·u + 0.5 로 옮긴다(이전에는 2^o·u). 방향·기술자 계산은 옥타브 안 화소 번호 좌표를 그대로 쓰므로 바뀌지 않는다.
- 공개 함수 `dominant_orientations`, `describe` 는 넘겨받은 영상의 화소 번호 규약 좌표를 받는다(문서에 적음). 특징점 좌표를 넣으려면 0.5 를 뺀다.
- 해시: FNV-1a 64비트, 특징마다 x, y, σ, 응답, 방향, 기술자 128개의 f32 비트를 순서대로. 변경 전 출력의 해시는 08d5248 에서 같은 함수(좌표 오프셋 인자 0 과 0.5)로 계산했다.
- 덩어리 렌더: 화소 (x, y) 값을 연속 좌표 (x + 0.5, y + 0.5) 에서 잰 가우시안(카메라 규약). 회전·축척 시험의 무늬 영상은 화소 번호 (w/2, h/2) 중심으로 그려 두었으므로 기대 위치 계산의 중심을 (w/2 + 0.5, h/2 + 0.5) 로 바꿨다(영상은 그대로).
- 측정은 4 코어 측정 기계, 동시 부하 있음. 5점 시간 시험(two_view `five_point_terminates_on_many_seeds`)이 전체 실행에서 부하로 실패했고 단독 1 스레드 실행에서 통과했다(검출과 무관).

## 남은 문제
- 호환성: `Keypoint::x, y` 의 의미가 바뀌었다. 예전처럼 +0.5 를 더하던 호출자는 이제 0.5 px 반대로 치우친다. `Intrinsics::index_to_normalized` 는 특징점용으로 쓰면 안 되고(+0.5 두 번), camera.rs 모듈 문서의 "특징점 `Keypoint::x, y` 가 이 규약" 문구와 README 예시(+0.5 / index_to_normalized)는 고쳐야 한다(이 묶음 밖 파일).
- undistort.rs 는 "화소 (i, j) 의 값은 연속 좌표 (i, j)" 규약으로 주점을 (cx + 0.5)·s − 0.5 로 옮긴다. camera.rs 의 화소 중심 규약과 어긋나 보인다(축척 s 에서 주점이 0.5·(1 − s) px 치우침). 확인 필요.
- matching.rs 시험 `scene_pair_cams` 의 정답 깊이 조회는 `k.x.round()` 로 화소를 고른다. 화소 중심 규약에서는 `floor` 가 맞다(이웃 화소 깊이를 볼 수 있음, 정답 판정에만 영향). 맡은 범위 밖이라 두었다.
- 해시 상수는 x86_64 Linux 의 std 수학 함수(exp, atan2 등) 결과에 묶여 있다. 다른 플랫폼에서 다르면 기대값을 플랫폼별로 둘지 정한다.
