# 보조 사진 설정별 비용·효과 (960x540 vs 320x240, F-343)

## 결론
- 960x540 기본 장면에서는 보조 사진 기본값(앞 40·뒤 40·뒤 간격 1)으로 7/7, 등록 81/81 이 다시 확인됐다. run 80.8 s.
- 뒤쪽 보조를 끄면(`--helper-back 0`) 5/7, 61/81 로 고치기 전과 똑같이 돌아간다(구역 0 이 14/42). 앞쪽 보조는 구역 1·2 에 이미 충분했고, 구역 0 에는 뒤쪽 보조가 꼭 필요하다.
- 뒤쪽 간격 4(`--helper-back-step 4`)는 960 에서 7/7 이고 구역 0 의 보조가 26 → 8 장으로 줄지만 run 시간은 82.9 s 로 간격 1(80.8 s)과 차이가 없었다(시간은 부하 변동 안). 정렬 점쌍·겹침 차는 비슷하고 preview_vs_refined 만 조금 나쁘다(최근접 0.466 → 0.597 m, 높이 차 0.311 → 0.527 m).
- 보조를 전부 끄면(앞·뒤 0) 3/7, 35/81. 구역마다 한 카메라만 등록된다.
- 320x240 은 어느 설정에서도 3/7(전부 끄면 2/7)로 고쳐지지 않는다. 기본값에서 등록 31/81, refined_overlap 5.0 m(앞서 측정한 41.0 m 는 뒤쪽 보조만 끈 설정에서 재현). 뒤쪽 보조를 넣어도 구역 0 의 F·L 은 등록 0/28 이라 보조 사진이 도움이 되지 않는다. 보조 사진 설정만으로 320 은 해결되지 않고 `--span 48` 같은 다른 처방이 필요하다.

## 방법
- 제품 `feat/region-cross-extend` 85dd7fe 를 별도 작업 트리에서 release 로 빌드(빌드 병렬도 2). 설정마다 `run d<크기>/in <출력> [옵션]` 다음 `verify <출력>` 을 순서대로(병렬 없이) 한 번씩 돌렸다. 반복 측정은 하지 않았다.
- 시간은 `run` 한 번의 벽시계 시간(verify·synth 제외). 960 합성은 3분 21초, 320 합성은 26초 걸렸다.
- 구역당 사진 수는 run 출력 사건 줄과 report.json 의 events 에서 읽었다. refined_overlap·preview_vs_refined 는 verify 표의 "중앙 최대" 값이다.
- 제품 코드는 고치지 않았다.

## 남은 문제
- 320x240 은 보조 사진으로 고쳐지지 않는다. 구역 0 등록 표에서 F·L 은 전부 미등록, 보조로 들어간 R 만 등록된다(기본 설정 기준 R 27/27, 나머지 0). 작은 영상에서는 먼 위치 쌍이 특징 매칭으로 이어지지 않는 것으로 보이나, 원인(특징 수·매칭 기준·겹침 면적)은 이 묶음에서 가르지 않았다.
- 320 의 refined_overlap 은 설정에 따라 0.66~41 m 로 크게 흔들린다(back 0 에서 41.0 m, 기본 5.0 m, 간격 4 에서 8.9 m). 등록 31/81 인 상태의 숫자라 설정 효과로 읽기 어렵다.
- 앞쪽 보조의 단독 효과(front 0, back 40)는 재지 않았다. (b)(d)만으로는 앞쪽의 기여를 분리하지 못한다.
- 간격 4 는 시간 이득이 측정되지 않았고 960 에서 preview_vs_refined 가 조금 나빠졌다. 단일 실행이라 차이가 잡음인지 알 수 없다.
- 320 의 `--span 48` 7/7 은 이번에 다시 돌리지 않았다(앞선 실험 결과 인용).
- verify 표의 기준 열은 "(240/240)" 으로 적혀 있는데 장면은 81장이다(기준 문구만 이상하고 판정은 81 기준으로 맞게 나온다).
