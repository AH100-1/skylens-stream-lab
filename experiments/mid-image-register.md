# 중간 크기 사진(480x270) 등록이 54/81 에 머무는 원인

## 결론

- 원인은 특징 수 상한이 아니다. 480x270 은 사진당 특징이 약 950(897~991)이라 상한 1500 에 걸리지 않는다. `--max-features` 를 1500/3000/5000 으로 바꿔도 결과가 완전히 같다(특징이 상한보다 적으니 당연하다). 이전 노트의 "상한 1500 에 걸린다" 가설은 틀렸다.
- 54/81 의 실제 원인은 **F–L(카메라 0–2) 짝이 쓸 만한 회전을 못 내서 L 카메라 27장이 통째로 빠지는 것**이다. 등록 표는 `cam0 27, cam1 27, cam2 0`(F·R 만 등록). F–R 짝은 정상(예약 10쌍 중 7쌍 검증, 정상 대응 135~184).
- F–L 짝은 구역 0 에 예약된 10쌍(위치 차 20..26)의 비율 검사(0.8) 통과 대응이 중앙값 5(최대 10)로 최소 20개 문턱 아래라 전부 탈락한다. 같은 장면에서 해상도별 F–L 대응 중앙값은 480x270: 5, 640x360: 13, 960x540: 29.5 로 해상도에 거의 선형이다. 960x540 은 7쌍이 20 이상이고 4쌍이 검증돼 81/81 이다.
- 문턱 완화는 해결책이 아니다. 비율 0.9 로 하면 F–L 10쌍 모두 대응 20 이상(중앙값 75)이 되지만 RANSAC 이 한 쌍도 받아들이지 않는다(겹침이 실제로 거의 없는 짝). 비율 0.95 는 F–R 도 망쳐 27/81 로 나빠진다. 최소 대응 10 은 변화 없음.
- 확대 검출을 켜도(특징 3000 으로 확대가 작동하게 함) 등록은 54/81 이다. 이때 F–L 7쌍이 RANSAC 을 통과(정상 25~49)하지만 **7쌍 중 4쌍은 상대 회전이 정답과 77~91° 어긋난 틀린 해**이고 3쌍만 맞다(0.0~2.2°). 회전 평균이 틀린 해 쪽으로 L 을 놓고 간선을 10° 기준으로 쳐내면서 L 이 다시 빠진다. 즉 480x270 에서는 대응이 모자란 데다 모자란 대응에서 나온 틀린 해가 맞는 해를 이긴다.
- 특징 상한을 해상도 비례로 두는 안은 효과가 없으므로 제안하지 않는다. 대신 제안(코드 미수정, 아래 남은 문제 참고).

- 480x270 사진당 특징: 최소 897, 중앙 954, 최대 991(확대 없음).
- 확대 검출 행은 small-image-features 브랜치의 features.rs(확대는 원래 검출 수가 목표의 절반 미만일 때만 작동)로 측정했다. 이 조건에서는 기본 상한 1500 일 때 480x270 은 확대가 작동하지 않아 확대 없는 행과 같고(954 ≥ 750), 상한 3000 일 때만 작동한다.
- 확대 + 특징 3000 에서 F–L 7쌍의 상대 회전 오차(정답 대비): 위치 0→20: 78°, 1→21: 85°, 2→22: 91°, 3→23: 1.4°, 4→24: 77°, 5→25: 2.2°, 6→26: 0.0°. F–R 7쌍은 모두 0.2~0.6°.
- 구역 0 인자 없는 기본 경로는 구역 3개라 구역마다 등록이 갈린다. F–L 이 구역 어디서도 검증되지 않는다(구역 0 의 F–R 은 검증).
- 정답 대비 포즈 오차는 등록된 카메라에서만 잰 값이다. 등록이 늘지 않았으므로 정확도 변화는 의미가 작다(확대 검출은 같은 54장에서 0.40 → 0.24 m 로 줄임).

## 방법

- 제품 main(779edb7) 릴리스 빌드에 측정용 임시 출력(짝별 대응 수, RANSAC 결과, 회전 평균 전·후 간선 오차)과 환경 변수(비율·최소 대응·카메라 간 간격·RANSAC 문턱)를 넣어 측정했다. 제품 브랜치에는 올리지 않았다.
- `synth <폴더> 480 270` → `run --stride 3 --span 48 ...` → `verify`. 포즈 오차는 `poses.txt` 와 `truth/cameras.txt`(C = -Rᵀt)를 비교해 중앙값 이동을 뺀 값.
- F–L 회전 오차는 짝별 상대 회전을 정답 상대 회전(R_j R_iᵀ)과 비교(전치도 시험해 작은 쪽).
- 카메라 번호는 0=F, 1=R, 2=L.

## 남은 문제

- 코드 변경은 하지 않았다(제품 브랜치 푸시 없음). features.rs 쪽 확대 조건은 다른 묶음 소관이라 제안만 한다.
- 제안 1(features.rs): 확대 조건을 "검출 수가 목표의 절반 미만" 에서 "검출 수가 목표 미만 또는 긴 변 800 미만" 으로 두면 480x270 도 확대가 작동한다. 다만 이것만으로는 54/81 이 안 풀린다(위 표). 시간은 약 4배(42 → 186 s).
- 제안 2(matching.rs 또는 RANSAC 후보 선택): 480x270 의 근본 문제는 F–L 의 틀린 해(77~91°)다. 방법 후보: 후보 해가 여러 개면 가장 정상 수 많은 것만 쓰지 말고 같은 카메라 쌍의 다른 위치 짝들과 상대 회전이 일치하는 후보를 고른다(F–L 은 같은 장착이라 위치와 무관하게 상대 회전이 거의 일정). 이번에 틀린 해 4개가 서로 비슷한 각(77~91°)이므로 쌍 단위 투표로 걸러질 가능성이 있다. 미검증.
- 제안 3(회전 평균): 카메라 쌍 단위로 간선 중앙값 회전과 비교해 틀린 해를 먼저 빼고 평균하면 맞는 3쌍으로 L 이 연결될 수 있다. 미검증.
- 특징 상한을 해상도 비례(예: 긴 변 480 → 3000)로 두는 안은 확대 검출과 함께일 때만 의미가 있고 단독 효과는 없다.
- 이번 측정은 한 장면·한 번씩이다(반복 없음).
