# benchmarks-scale — 측정 틀 하나로 합침, 번들 조정 실제 규모, 검출 시간 기록 (T14, F-040·F-031·F-113)

## 결론
- **측정 틀을 `crates/core/benches/pipeline.rs` 하나로 합쳤다.** 예제 `examples/bench_stages.rs` 는 지웠다.
  이유: 두 틀이 같은 구간(렌더·검출·매칭·두 시점·회전 평균·번들 조정)을 같은 공개 API 로 따로 재고 있어
  인자·문제 생성 코드가 두 벌이었다. 반복·중앙/최소를 내는 쪽(bench)을 남기고, 예제에만 있던 두 가지 —
  (a) 이 실행의 두 시점 결과(정상 대응 수 가중)로 회전 평균을 돌리고 정답 대비 정렬 오차를 내는 것,
  (b) JSON 출력 — 을 bench 에 옮겼다(`회전 평균(검증 결과)` 줄, `--json PATH`). bench 는 `cargo bench` 만으로 돌고
  `clippy --all-targets` 검사를 받으며, 예제는 따로 실행 경로를 알아야 해서 잊히기 쉽다.
- **F-040: `--mode ba-scale` 을 넣었다**(공개 API `bundle_adjust`·`BaOptions` 만 사용). 카메라 240·트랙 10만에서
  관측 366만 5717(평균 트랙 길이 36.7)이 생겼고, **반복당 약 97 s, 3회 전체 293.5 s** 였다. 단 측정 중 부하 평균이 27~37
  (4 코어에 다른 빌드·시험 여러 개)이라 단독 실행보다 수 배 느린 값이다. 감독 단독 측정(관측 275만, 반복 1회 15.0 s)과
  같은 자릿수 비례(관측당 약 5.5 μs/반복 단독 대비 약 26 μs/반복)로, 부하 배수(약 5배 이상)와 맞는다.
  가림을 무시해 트랙이 실제보다 길다(아래 남은 문제).
- **F-031: `--mode detect`** 로 합성 1920×1080 한 장 검출 시간을 F-014 기준 0.4 s 와 함께 기록한다(단언 없음).
  회귀 판정은 이미 `cargo test --release` 에서 도는 `tests/perf_structure.rs::detection_hash_regression`
  (검출 해시, 부하와 무관)과 연산량 구조 시험 4개가 맡는다. 이번 측정 2.54 s(중앙, 5회)는 부하 평균 37 아래 값이라
  시간 기준이 부하에 얼마나 흔들리는지 보여 준다 — 벽시계 단언을 기본 시험에 넣지 않는 근거.
- F-113(깊이 융합 시간)은 이 틀에 아직 없다. 융합 단계 입력(깊이 지도들)을 만드는 공개 경로가 이 틀 범위 밖이라 남겼다.

## 수치

모두 **4 코어 측정 기계, 동시 부하 있음**(다른 빌드·시험이 함께 돎, 각 표에 부하 평균). 절대값은 단독 실행보다 크게
부풀어 있으므로 구간 사이 비율·규모 감만 본다.

### A. 번들 조정 실제 규모 — `cargo bench --bench pipeline -- --mode ba-scale --ba-iters 3 --repeat 1`

카메라 240(위치 80 × 3, 960×540 내부 파라미터, 그룹 3), 트랙 100000(관측 2 이상 99875), 관측 3,665,717,
평균 트랙 길이 36.66, 문제 생성 3.2 s. 카메라 0·1 고정, Huber(2), `function_tolerance = 0`(조기 종료 없음).
부하 평균 26.7(시작) → 36.6(끝). rayon 스레드 4(번들 조정 자체는 단일 스레드).

| 실행 | 반복 | 시간 (s) | RMS (px) | 비고 |
|---|---:|---:|---|---|
| 반복 0(트랙 선택·배치·평가만) | 0 | 2.315 | 5.105 | |
| 반복 1 | 1 | 108.55 | 5.105→0.702 | 반복 1 − 반복 0 = 106.2 s |
| 반복 3 | 3 | 293.55 | 5.105→0.694 | 수렴 false(3회 상한) |
| **반복당 (3회 − 0회)/3** | | **97.08** | | |

SPEC §5 정밀 포즈 ~270 s(GPU)에 비하면 이 부하 아래에서는 3회만에 넘는다. 단독 실행 반복당 값은 감독 측정
(관측 275만 15.0 s)으로 미루어 관측 367만에서 약 20 s 로 추정되며, 50회면 약 1000 s 이다.

## 방법
- 사용법(합친 틀): `cargo bench --bench pipeline -- [인자]`

  | 인자 | 기본값 | 뜻 |
  |---|---|---|
  | `--mode M` | `pipeline` | `pipeline` / `ba-scale` / `detect` |
  | `--positions N` | 80 | 촬영 위치 수(영상·카메라 3N) |
  | `--width W` `--height H` | 960 540 | 렌더 해상도(`ba-scale` 은 내부 파라미터 크기로만 씀) |
  | `--repeat R` | 3 | 반복 → 중앙·최소(`ba-scale` 은 반복 0 실행에만 적용) |
  | `--threads T` | 0 | rayon 전역 스레드 수 |
  | `--max-pairs P` | 0 | 매칭·검증·자세에서 잴 짝 수 상한 |
  | `--ba-points M` | 20000 | `pipeline` 번들 조정 점 수 |
  | `--ba-tracks N` | 100000 | `ba-scale` 트랙 수 |
  | `--ba-iters K` | 3 | `ba-scale` 반복 수 |
  | `--json PATH` | | `{cores, threads, mode, rows[{name, items, unit, median_s, min_s, note}]}` |
  | `--quick` | | 24장 480×270 |

- `ba-scale` 문제: 정답 포즈(렌더 없음). 트랙 k 는 영상 k mod 240 의 균등 난수 화소를 깊이 10~60 m 로 역투영,
  모든 카메라에 투영해 깊이 1~80 m·영상 안이면 관측(가림 무시, 0.5 px 잡음). 포즈 0.2°·5 cm, 점 5 cm 흔듦.
  반복당 시간은 내부 구간을 들여다보지 않고(공개 API 만) 반복 0·1·K 실행 시간 차로 낸다. 반복 0 이 트랙 선택·
  배치·첫 비용 평가를 담으므로 빼면 선형화·슈어 소거·촐레스키·감쇠 재시도·재평가를 합친 반복 비용이 남는다.
- `detect`: `Scene::new(positions 1, 1920×1080)` 첫 영상, 예열 1회 뒤 R 회.
- 회귀 판정(부하 무관)은 기존 `tests/perf_structure.rs` 5개(짝 수 선형식, 기술자 비교 상한, 옥타브 σ 상한,
  RANSAC 반복 수, 검출 해시)가 맡는다. 이번 묶음은 제품 코드·시험을 고치지 않았다.

## 남은 문제
1. 모든 수치가 부하 평균 15~37 아래 값이다. 부하 없는 때 세 모드를 다시 돌려 표를 바꿔야 한다.
2. `ba-scale` 은 가림을 무시해 평균 트랙 길이가 36.7 로 실제(감독 측정 약 26, 이전 측정 6.5)보다 길다.
   트랙 길이 상한 인자(예: 카메라 중심 거리순 상위 L 개)를 넣어 관측 수를 실제 분포에 맞춘 줄을 더해야 한다.
3. 반복당 시간을 선형화·슈어·촐레스키로 나누려면 `ba.rs` 내부 시간 계측이 필요하다(공개 API 만으로는 불가).
   `feat/ba-hardening` 의 `ba_scale_timing`(무시 시험)이 그 분해를 하므로 둘을 같은 문제 생성으로 맞추는 일이 남았다.
4. F-113 융합 시간 측정 모드가 없다(48장 960×540 융합, 목표 2 s).
5. `tests/perf_structure.rs` 머리 주석이 지운 예제 `examples/bench_stages.rs` 를 가리킨다. 맡은 파일 밖이라 고치지 못했다
   (`benches/pipeline.rs` 로 바꿔야 함).
6. 틀 머리 줄은 모드와 무관하게 위치·해상도 인자를 찍는다(`detect`·`ba-scale` 에서는 실제 쓰인 값과 다를 수 있음).
