# 구역 2 초벌 축척 1.178 의 출처와 구역 간 스케일 검사

## 결론

- 구역 2 초벌 모델이 18 % 작은 것은 카메라 중심 전체의 축척 문제가 아니다. 위치 풀이(방향 제약 + GPS 사전 선형 최소제곱) 뒤 카메라 중심의 정답 대비 축척(중심 Umeyama)은 구역 2 가 1.018, 구역 1 이 1.011 로 맞다.
  틀어지는 것은 한 위치의 카메라 3대 사이 간격(장비 안 기준선, 정답 9.8 m)이다. 구역 2 에서 위치 풀이 결과는 정답의 0.792, 점을 만들기 직전(위치 다듬기 뒤) 0.848 로 줄어 있다.
  삼각측량 점의 깊이는 이 기준선에 비례하므로 점은 1/0.848 = 1.18 배 작아진다. 실제 초벌 점 → 정밀 점 정렬 축척 1.1778 과 맞는다.
- 원인은 GPS 잡음이다. 기본 경로(위치 평균이 아니라 `GpsLeastSquares`)에는 GPS 로 축척을 따로 맞추는 단계가 없고, 축척은 GPS 사전항(가중 1)이 방향 제약(축척을 정하지 못함)과 겹쳐 정한다.
  GPS 가 정답과 같은 장면(잡음 0)으로 같은 실행을 하면 구역 2 정렬 축척은 1.0060, 구역 1 은 0.9984 이고 장비 안 기준선 비는 0.977/0.991 이다. 잡음 GPS(정답 대비 중앙 3.3 m, p90 4.5 m)에서는 구역 2 1.1778 이다.
  구역 2 는 둘째 주축 폭(정답 표준편차 1.50 m)이 GPS 잡음(3.3 m)보다 작고, 구역 안 자기 사진은 10 장(3 위치)뿐이라 나머지 22 장은 앞 구역에서 온 도우미 사진이다. 잡음이 장비 안 간격(9.8 m)을 줄여도 방향 제약만으로는 간격의 길이를 바로잡지 못한다(방향 제약은 거리를 정하지 않는다).
  구역 1 은 같은 잡음에서도 장비 안 기준선 비 0.922(위치 풀이)·0.918(최종)이지만 점 정렬 축척은 1.0024 이다. 곧 구역 1 은 기준선이 8 % 줄었는데 점 축척은 맞으므로 "기준선 비 하나로 점 축척이 정해진다" 는 설명은 구역 2 에서 두 수가 맞는 것뿐이고 구역 1 에는 맞지 않는다(남은 문제).
- 가름: 위치 풀이(= GPS 정렬을 대신하는 단계)가 원인이다. 그 뒤 위치 다듬기(`refine_centers`)와 삼각측량은 축척을 거의 안 바꾼다(최종/위치 풀이 중심 축척 0.9988~0.9972). GPS 잡음을 없애면 사라지므로 점 정렬(정밀 쪽)이나 정렬 코드의 오류가 아니다.
- 구역 간 스케일 검사는 이 18 % 를 통과시키지 않고 잡는다. 허용치 `ALIGN_SCALE_TOL` = 0.10 (max/min − 1)에 값은 0.175 이므로 스트림 실행의 `issue 구역 간 스케일 차 0.175 > 0.1 (최소 1.0024, 최대 1.1778)` 가 나온다.
  단 구역 0 은 정렬 기록의 축척이 null(점 쌍 0)이라 검사 대상이 구역 1·2 두 개뿐이다. 그리고 `verify` 의 preview_align 은 구역 0 의 `fit_median_m` 이 null 이라 스케일 비교에 닿기 전에 "숫자가 아님" 오류로 FAIL 한다(잡음 0 인 장면에서도 같다). 두 번째는 이번 묶음에서 고치지 않았다.
- 이번에 동작은 바꾸지 않았다(진단 필드와 환경 변수 덤프만). 대안 한 가지(실험 안 함): 아래 "남은 문제" 참조.

## 방법

- 제품에 진단 필드 `PreviewStages::avg`(위치 평균을 쓸 때 GPS 맞춤 전 중심·축척·남은 대응; 기본 경로에서는 None)와 환경 변수 `SKYLENS_ZONE_DUMP=<폴더>` 덤프 `zone_scale_NN.txt`(사진마다 번호, GPS, 위치 풀이 뒤 중심, 최종 초벌 중심)를 넣었다. 환경 변수가 없으면 출력·동작은 같다. `averaged_centers` 는 진단을 함께 돌려주게 되었다.
- 기본 경로의 실제 흐름을 코드로 확인했다: 회전 평균 → 좌표계 맞춤(Kabsch, 방향만) → `stand_in::solve_centers`(방향 제약 + GPS 사전, `prior` 1.0) → `refine_centers` → 삼각측량(번들 조정 없음). 위치 평균(`averaged_centers`)의 축척 맞춤 `s` 는 `--position translation-averaging` 일 때만 쓰이고 기본에서는 거치지 않는다. 과제 문면의 "위치 평균 → GPS 정렬" 은 기본 경로가 아니다.
- 시험 `zone_scale_origin`(무시, 약 4.5 분): 같은 합성 장면을 잡음 GPS 와 정답 GPS(gps.txt 를 정답 카메라 위치로 다시 쓴 장면) 두 번 돌려위 표를 낸다. 기준값 단언은 잡음 장면에서 구역 2/구역 1 정렬 축척 − 1 > 허용치(= 검사가 잡는 규모).
- 구역 정렬 축척은 manifest.json 의 align 기록, 스케일 검사 결과는 실행 출력의 `issue` 줄과 `verify` 출력.
- 점 정렬 축척과 기준선 비 사이 대응(1/0.848 ≈ 1.18)은 구역 2 한 곳에서만 확인했다. 구역 1 은 기준선 0.92 인데 축척 1.002 로 대응이 없다.

## 남은 문제

- 구역 1 에서 기준선 비와 점 축척이 대응하지 않는 이유를 설명하지 못했다(점 정렬은 구역 전체 안쪽 쌍 2533 개, 구역 2 는 먼 쪽을 거른 706 개; 앞 노트). 장비 안 기준선이 점 축척을 정한다는 것은 구역 2 의 정황 증거일 뿐 인과 시험(기준선만 고쳐 넣기)은 하지 않았다.
- 대안 한 가지(측정 안 함): 위치 풀이에서 장비 안 카메라 간격은 구역 전체에서 하나의 값(구역 내 사진 3대 상대 위치 평균)으로 묶어 GPS 잡음이 간격을 누르지 못하게 한다. 잡음 0 장면에서 축척 1.006 이 나오므로 상한이 보인다. 구현 전에 구역 1·2·3(다른 시드)에서 확인이 필요하다.
- `verify` 의 preview_align 은 구역 0 정렬 기록(null)에서 오류로 끝나 스케일 검사에 닿지 못한다(잡음 0 장면에서도 같음). SPEC §3.7 이 구역 0 도 정렬하라고 하므로 기록을 채우거나 null 을 건너뛰어야 한다.
- 정답 GPS 장면의 GPS-정답 거리 2.00 m(일정)의 정체 확인.
