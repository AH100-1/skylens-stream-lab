# benchmarks — 구간별 시간 측정 틀 (T14 첫 단계, FEEDBACK F-031 시간 부분)

## 결론
- 제품에 `crates/core/benches/pipeline.rs`(`harness = false`, 외부 측정 크레이트 없이 `std::time::Instant`)를 두었다.
  합성 장면(SPEC §6)을 만들고 합성 렌더 → 특징 검출 → 짝 생성 → 비율 매칭 → RANSAC F(8점)·E(5점) → 두 시점 자세 →
  회전 평균 → 번들 조정을 구간마다 같은 입력으로 R 회 돌려 중앙·최소를 표로 출력한다. 첫 줄에 코어 수·rayon 스레드 수를 찍는다.
- F-031 의 시간 부분: 검출·매칭 시간이 이제 `#[ignore]` 시험 밖에서도 이 틀로 재진다. CI 에는 넣지 않고 감독 실행 때 돌린다.
  시간 단언은 하지 않는다.
- 작은 규모 측정에서 **기하 검증 E(5점) RANSAC 이 가장 비싸다**(짝당 160~210 ms, 대응 50~150 개뿐인 짝에서도).
  매칭(짝당 6~24 ms)·F RANSAC(14~18 ms)보다 한 자릿수 크다. 240장 전체(짝 약 3700개)에서는 E RANSAC 만 단일 실행으로
  수 분이 될 것으로 보이며, T14 병렬화의 첫 대상이다.
- 240장 전체는 320×180 에서 한 번 쟀다(예제 `bench_stages`, 아래 C 표): 렌더 제외 262 s 중 **두 시점 검증이 209 s(80%)**,
  번들 조정 37 s, 검출 8.5 s, 매칭 7.5 s, 회전 평균 0.2 s. 동시 빌드 부하(부하 평균 4.7) 아래 측정이라 재측정이 필요하다.
  960×540·1920×1080 240장 측정은 하지 못했다(아래 남은 문제).
- F-031 의 회귀 부분: 벽시계 대신 연산량을 숫자로 고정한 일반 시험 `crates/core/tests/perf_structure.rs`(5개)를 두었다.
  짝 수 선형식(48P − 177), 특징 수 상한에 의한 기술자 비교 수 상한, 옥타브 수별 최대 스케일, RANSAC 반복 수,
  고정 480×270 합성 영상의 검출 결과 해시(753 개, 0x618def587be02b14). `cargo test --release` 에서 돈다.

## 방법
- 사용법: `cargo bench --bench pipeline -- [인자]`

  | 인자 | 기본값 | 뜻 |
  |---|---|---|
  | `--positions N` | 80 | 촬영 위치 수(영상 3N장, 기본 240장) |
  | `--width W` `--height H` | 960 540 | 렌더 해상도(`SceneConfig` 기본) |
  | `--repeat R` | 3 | 구간마다 같은 입력 반복 횟수 → 중앙·최소 |
  | `--threads T` | 0 | rayon 전역 스레드 수(0 = 논리 코어 수) |
  | `--max-pairs P` | 0 | 매칭·검증·자세에서 잴 짝 수 상한(0 = 전부, 짝 목록에서 고르게 뽑음) |
  | `--ba-points M` | 20000 | 번들 조정 점 수 |
  | `--quick` | | `--positions 8 --width 480 --height 270 --repeat 3 --ba-points 3000` |

- 짝: `candidate_pairs(PAIR_TEMPORAL, PAIR_CROSS, PAIR_POW2_MAX)`(제품 기본). 매칭은 비율 0.8·상호 확인, 짝은 차례로 돌리고
  짝 안에서 병렬(제품 구현 그대로). RANSAC F·E 와 두 시점 자세는 짝 사이 rayon 병렬. E 는 `ransac_essential`(초점 = 정답 fx,
  `RansacConfig` 기본), 자세는 그 정상 대응으로 `recover_pose`.
- 회전 평균·번들 조정 입력은 매칭 결과가 아니라 정답에서 만든다: 전체 짝 그래프에 정답 상대 회전 + 0.2° 잡음(가중 100);
  깊이 지도에서 고르게 뽑은 점을 깊이 1~80 m·영상 안인 모든 카메라에 투영(가림 무시) + 0.5 px 잡음, 자세 0.2°·5 cm,
  점 5 cm 흔들기, 카메라 0·1 고정, 카메라 종류별 내부 파라미터 그룹 3개. 짝 수 상한과 무관하게 전체 그래프 크기로 재기 위해서다.
- 구간마다 결과를 `black_box` 로 넘겨 최적화로 사라지지 않게 했다. 첫 반복은 데우기 효과가 섞이므로 최소값도 함께 적는다.
- `cargo clippy --all-targets -- -D warnings` 가 bench 도 검사하며 통과.
- 예제 틀: `cargo run --release -p skylens-core --example bench_stages -- [--width W --height H --positions N --threads T --json PATH]`
  (기본 320×180, 80 위치 = 240장; `--width 1920 --height 1080` 선택). 영상마다 `detect_and_describe` 를 차례로(검출 내부 병렬),
  짝마다 `ratio_match(0.8, 상호)` 를 차례로, 두 시점 검증은 짝 사이 rayon 병렬로 `ransac_essential_candidates`(초점 = 정답 fx,
  `RansacConfig` 기본) 1위 후보 → 정상 대응으로 `recover_pose`. 대응 15개 미만 짝은 건너뛴다. 그 상대 회전(정상 수 가중)으로
  `average_rotations` 기본 설정. 텍스트 표와 JSON(`images, width, height, threads, stages[{name, seconds, detail}], total_seconds`).
- 구조 시험(`tests/perf_structure.rs`), 근거는 시험 주석:
  - 짝 수 = 48P − 177 (P = 20, 40, 80, 160), 240장 3663 짝, 장당 이웃 ≤ 32 이고 경로 가운데는 정확히 32.
  - 480×270 에서 기본 검출 > 200 개, `max_features = 200` 이면 180~200 개 → 짝당 기술자 비교 ≤ 200².
  - 옥타브 o 의 최대 σ ≤ σ0·2^(o−1)·2^(4/3), o > 1 이면 한 옥타브 아래 상한보다 크다(o = 1, 2, 4).
  - `adaptive_iterations`: (0.5, 5) → 218, (0.8, 8) → 바닥 50, (0.1, 5) → 상한 2000.
  - 검출 해시: (x, y, σ, 응답, 방향) f32 비트의 FNV-1a 64, main 08d5248 에서 계산. 스레드 1개에서도 같은 값.

## 남은 문제
1. 240장 기본 규모(960×540) 측정과 SPEC 해상도(1920×1080) 측정이 없다. 부하 없는 때 `cargo bench --bench pipeline`
   (짝 전체가 길면 `--max-pairs 400`)으로 표를 채워야 한다. 렌더만 240장 × 수백 ms 이상이다.
2. E(5점) RANSAC 이 짝당 160~210 ms 로 가장 비싸다. 대응 수가 적은데도 비싼 것은 최소 반복(`ESSENTIAL_MIN_ITERS` 300),
   평면 검사, 후보 다중 정밀화 때문으로 보이며 원인 분해는 하지 않았다.
3. 회전 평균이 두 실행 모두 최대 반복 50 에 닿았다(정답 + 0.2° 잡음 입력에서도). 수렴 문턱 1e-10 rad 이 잡음 있는 입력에서
   너무 엄격한 것으로 보인다. 정확도 문제는 아니지만 시간 측정 해석 때 주의.
4. 검출 해시 회귀 시험은 `perf_structure.rs::detection_hash_regression` 으로 넣었다. 흐림 커널 합 순서를 일부러 바꿔
   실패하는지 확인하는 일(F-031 확인 기준)은 기존 모듈을 고치지 않는 범위라 하지 못했다. 다음에 임시 수정으로 확인해 적어야 한다.
5. 번들 조정 관측은 가림을 무시한다(시간 측정용). 실제 트랙 길이 분포와 다를 수 있다.
6. 회전 평균·두 시점 검증 결과가 C 표처럼 정답 대비 수치를 내지만 시간 틀일 뿐 정확도 기준은 아니다.
7. 측정 틀이 두 개다(`benches/pipeline.rs` 와 `examples/bench_stages.rs`). 앞의 것은 반복·중앙값, 뒤의 것은 매칭 결과로
   실제 두 시점 검증·회전 평균을 이어 돌리고 JSON 을 낸다. 하나로 합칠지 정해야 한다.
