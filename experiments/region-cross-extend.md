# 구역 복원용 보조 사진으로 기본 경로 7/7 (F-343, 구역 소유 위치 유지)

## 결론
SPAN 12·OVL 2 와 구역의 소유 위치(출력·점·집계 대상)는 그대로 두고, 구역을 복원할 때만 구역 밖 뒤쪽 R·L 사진을 보조로 더 넣었다
(앞쪽 F 보조는 기존 그대로). 인자 없는 synth → run → verify 가 종료 0, 7/7, 등록 81/81(초벌·정밀), 구역 3개로 바뀌었다.
원인은 구역 0(위치 0..14)의 F 와 L 이 R 과만 따로 놀던 것이었다: F(p)–R/L(p+20..+40) 짝의 상대 쪽이 구역 뒤에 있어 구역 안에 다른 카메라 짝이 없었다
(고치기 전 구역 0 등록 14/42, 구역 1·2 는 앞쪽 F 보조 덕에 이미 전부 등록).
보조 사진은 등록·BA 에만 쓰고 밀집·출력·등록 집계(`registered`, 점수)에서는 뺀다. 구역 완료 시점은 보조 사진까지 읽은 뒤다.

## 수치
기본 합성 장면(960x540, 27위치 81장), 4 코어 측정 기계, 다른 빌드 동시 부하(시간은 부하에 따라 흔들림).

정답 겹침 d 는 F-197 의 측정표를 인용했다(직접 다시 재지 않음): F→R 은 +12 부터 2%, +20 10%, +38 35%; F→L 은 +16 11%, +30 약 30%; R↔L 은 2% 미만.
제품 기본 일정(`CrossSchedule::FORMATION`)은 F(p)–R/L(p+20..+40, 4칸 간격)이다. 시험 `region_pair_schedule_has_cross_camera_pairs`:
장면 전체 일정에 다른 카메라 짝이 있는 소유 사진은 구역 안 일정에도 있어야 하며, 뒤쪽 보조를 끄면 이것이 깨진다(F 사진 0·1·3·4·5 번 위치).

## 방법
- `HelperConfig { front_span 40, back_span 40, back_step 1 }`(`PipelineConfig::helper`, run 옵션 `--helper-front/--helper-back/--helper-back-step`, 0 이면 끔).
- 뒤쪽 보조: 위치 [hi, min(hi+back_span, lo+back_span+1)) 의 R·L. 구역 시작 기준 위치 차 +40 까지만 넣는다. 구역이 41위치 이상(span 48)이면 뒤쪽 보조가 없다.
  처음엔 hi 기준 +40 까지 넣었더니 span 48 두 구역 장면(`pipeline_e2e::two_region_end_to_end`)의 중심 오차 최대가 3.115 → 5.559 m 로 나빠졌다(구역 0 은 이미 전부 연결돼 있는데 먼 R·L 이 추가됨). 구역 시작 기준으로 바꿔 해소.
- 보조 사진은 gids 앞쪽에 모아 `n_help` 로 구분(등록 집계·중심 출력·정지 검사 제외, 밀집 대상 아님). 정지 검사는 인덱스 기준으로 바꿨다.
- 흐름: 보조 사진도 위치 단위로 도착, 구역 밖 뒤 위치는 사건 `arrive_helper`(소유 위치만 `arrive_position`).

## 남은 문제
- 뒤쪽 보조 R·L 은 구역마다 다시 특징·매칭 비용이 든다(구역 0 에서 68장, 짝 수 증가). span 12 에서 매칭 시간은 구역 0 이 10.3 → 13.1 s 로 늘었으나 BA·밀집이 줄어 전체는 짧아짐.
- 구역 안에서 F(p) 가 R/L 과 연결되는 위치가 구역 앞쪽 몇 곳 안팎이라 연결 수는 적다(간격 1 이라 최소 1 개 이상). 회전 오차는 구역별로 재지 않았다.
- 장면 끝(마지막 구역)과 장면 앞(구역 1 의 R·L, 위치 10..19)은 F 가 없어 다른 카메라 짝이 원래 없다. GPS 사전으로 등록된다.
- 320x240 장면은 다루지 않았다. 다른 묶음의 '카메라별 이동 창' 안과 비교하지 않았다.
