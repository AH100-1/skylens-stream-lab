# 회차: 시간 시험 경로 정정·법선 단언 (2026-10-03, 4 코어 측정 기계)

## 결론
- `timing_960`(F-048 이름)은 기본 경로 `estimate`(= `estimate_fast`)가 아니라 이전 다단계 경로를 재고 있었다. 이제 `estimate` 를 직접 잰다. `estimate_profiled` 문서는 이전 경로 측정판이라고 고쳤다.
- 벽시계 ≤ 0.7 s 는 이번에도 확인하지 못했다. 측정 시 부하 평균이 20 이상이었다(4 코어). 기본 경로 벽시계 4.1~4.4 s 는 부하 때문이며 CPU 시간은 1.81 s(환산 0.45 s). 노트의 이전 문장은 CPU/4 를 근거로 F-048 충족이라 적었으나 확인 기준은 벽시계라 `experiments/patchmatch.md` 결론을 고쳤다.
- 기본 경로 최대 메모리 증가 49.5 MB(F-050 기준 50 MB 미만, 여유 0.5 MB 로 얇다). 이전 경로의 55.4 MB 는 기준 초과였다.
- `fast_960` 에 법선 중앙 < 5° 단언과, 환경 변수 `PM_MAX_S` 로 켜는 시간 단언을 넣었다. `PM_SK=0.08 PM_SP=0` 에서 법선 6.26° 로 실패한다.
- `skip_probes` 문서를 실제 동작으로 고쳤다(1 = 이웃 법선 평균 한 번, 2 이상부터 무작위 법선 섭동).

## 방법
- 빌드 `cargo test --release`, `timing_960` 안에서 `/proc/self/status` 의 VmHWM 을 추정 전후에 읽어 차이를 증가량으로 했다(같은 프로세스, 시험 1개 실행). 부하는 `/proc/loadavg`.
- 시작 시 부하 `6.57 2.02 0.71` 이었다가 측정 중 `20~23` 으로 올랐다(다른 작업이 동시에 돎).

## 남은 문제
- 부하가 낮은 기계에서 `PM_MAX_S=0.7` 로 `fast_960`, 그리고 `timing_960` 의 벽시계 ≤ 0.7 s 를 확인해야 한다. 이번 값은 부하 때문에 기준을 넘는다(4.4 s 대 0.7 s).
- 메모리 증가 49.5 MB 는 기준에 0.5 MB 차이라 측정마다 넘을 수 있다. 부하 낮은 기계에서 반복 측정 필요.
- 전체 `cargo test --release` 결과는 아래 커밋 시점에 적지 못했다면 제품 쪽 보고를 따른다.
