# PatchMatch 속도 정리 (시점별 깊이·법선, 960×540)

## 결론
- 이번 라운드에서 알고리즘은 바꾸지 않았다. 기본 경로(`estimate` → `estimate_fast`)는 이미 체커보드 병렬, 창 통계 캐시, 상위 3 집계, 피라미드(120 → 960), 성긴 창 표본, 수렴 화소 건너뜀을 쓴다.
- n 코어 측정 기계(4 코어)에서 부하 평균 1.4 일 때 960×540·이웃 8장 한 장은 0.53~0.59 s 로 목표 1 s 이하다. 부하 평균 17~19 일 때는 같은 코드가 3.35~3.42 s 로, 시간은 부하에 거의 비례한다.
- F-292: `timing_960` 은 이미 `estimate` 를 재고 `estimate_profiled` 문서도 이전 경로임을 밝힌다(61fa09a). 이번에 시간 시험 출력에 95분위 오차·유효 화소 비율을 더하고 단언을 붙였다.
- 부하 높은 상태에서는 CPU 시간(약 2.0 s)이 줄지 않는 한 1 s 를 보장할 수 없다. CPU 절감은 하지 못했다.

## 수치 표 (4 코어 측정 기계, 스레드 4)
| 항목 | 변경 전 = 변경 후(알고리즘 동일) |
|---|---|
| 한 장 시간, 부하 1.4 (3회) | 0.59 / 0.53 / 0.58 s |
| 한 장 시간, 부하 17~19 (3회) | 3.42 / 3.42 / 3.35 s |
| 한 장 CPU 시간 | 1.92~2.07 s |
| 깊이 상대오차 중앙값 | 0.198% |
| 깊이 상대오차 95분위 | 1.075% |
| 유효 화소 비율 | 100.0% |
| 깊이 1% 이내 | 94.4% |
| 법선 중앙값 | 4.01° |
| 추정 중 최대 메모리 증가 | 약 49.7 MB |

반복 수를 줄인 시도(`PM_IT`): 2 회는 법선 4.88°, 1 회는 12.01° 로 기준(5°)에 닿거나 넘어 채택하지 않았다.

## 방법
- 이번 변경은 시험뿐이다. 시험의 통계에 오차 95분위와 유효 비율을 추가하고 `timing_960` 에 95분위 < 3%, 유효 > 99% 단언을 붙였다.
- 기존 방식은 Galliani 2015 의 빨강·검정 병렬 전파, Goesele 2007 식 이웃 선택, Shen 2013 식 상위 k 비용 집계다.

## 남은 문제
- 부하가 높은 기계에서는 벽시계가 부하에 비례한다. 1 s 를 부하와 무관하게 지키려면 CPU 시간 자체를 줄여야 한다(가장 거친 층 반복, 원 해상도 층 시작 비용 계산 0.16~0.3 s 가 큰 몫).
- 가장 거친 층(너비 120)의 반복이 부하 아래에서 비정상적으로 길게 나온다(0.4~1.3 s). 원인은 미확인이다.
- 코어 전체 시험 `cargo test --release -p skylens-core --lib` 은 부하 평균 30 에서 1건 실패(어느 시험인지 기록하지 못함, patchmatch 시험 12개는 통과). 부하 낮은 때 재확인 필요.
